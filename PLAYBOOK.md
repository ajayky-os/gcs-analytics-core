# gcs-analytics-core · SIL Playbook

Durable, project-specific knowledge for the self-improving loop. The loop **reads this before every
iteration** and **updates it** whenever it discovers something that would have saved time.
Keep it factual and short. Ephemeral per-iteration notes belong in `LEARNINGS.md`.

## Build & test facts

- `GPKG_NOINFO=1` silences the corp-airlock banner that otherwise pollutes logs.
- Pre-commit hooks are installed in the checkout: `detect-secrets`, `end-of-file-fixer`, `trim-trailing-whitespace`, `addlicense`. A commit can be silently rewritten by them — re-check `git diff --stat` after committing.
- Spotless toggle in this repo is `fmt:off` / `fmt:on` (forbidden by the hygiene gate).
- Typical durations on this machine: build (Error Prone + jmh/integration sources) ≈ 40s, lint ≈ 3s, unit+coverage (1063 tests) ≈ 60s, JMH ≈ _needs bucket_.
- Known flaky tests: _none recorded yet_ (record name + failure signature + frequency; never @Disable them).
- The **primary checkout** `~/google-projects/gcs-analytics-core` has a `.git/hooks/pre-push` patent guard (go/idf, for the in-flight read-hedging work) that blocks *every* push to github.com. Never bypass it; push SIL branches from a hook-free clone (`~/google-projects/gcs-analytics-core-oss` or this repo) instead.
- `hygiene.title_regex` caps the conventional-commit description at **80 chars** — keep subjects short or the hygiene gate fails on title alone.
- `spotless:check` is bound to the `test` phase in `client`, so run `./mvnw -B -q spotless:apply` before every targeted test run.
- Targeted runs: `./mvnw -B -q -pl <module> -am test -Dtest=<Class> -Dsurefire.failIfNoSpecifiedTests=false` ≈ 30–40 s cold; stderr is flooded with "Application name is not set" — grep it out.
- Test idioms: `GcsReadChannel(storage, itemInfo, …)` eagerly calls `storage.reader(...)` once in its constructor → `Mockito.clearInvocations(storage)` before counting readers. `ReadAsFutureByteString` has value `equals`, so `verify(session).readAs(asFutureByteString().withRangeSpec(RangeSpec.of(o, l)))` works without captors. `VectoredIoUtil.canMerge` is strict (`gap < maxMergeGap`).
- java-storage semantics trap: `RangeSpec.of(offset, 0)` means **read to EOF**, not "empty" — never forward a zero-length range to a `BlobReadSession` (fixed in PR #406).
- **Cache probes**: never "probe" `AnalyticsCacheManager.getFooter/getSmallObject` with a throwing loader — the default footer cache is the NoOp impl (prefetch on, cache off), so the loader runs and throws on every call; with Caffeine it takes the compute lock. Use `getFooterIfPresent` (added in PR #405) / `AnalyticsCache.get(K)`.
- **Optimizer contract**: `SmartReadChannel.readVectored` has no try/catch — a `FormatOptimizer` that throws strands every later range future. Settle each future per range; return the original list only when nothing was attempted.
- **Stacked PRs**: hygiene measures `git diff base..HEAD` for the whole stack, so the upper PR must fit in `400 − lower PR lines`. Trim redundant verifies, never tests (critic rejects test removal).
- Mockito 5 returns `Optional.empty()` for unstubbed `Optional` methods — handy for "not cached" without stubbing.
- Integration tests need `-Dgcs.integration.test.bucket` (exported from `SIL_GCS_TEST_BUCKET`); gate SKIPs until set.
- **Pre-push hook blocks pushes to public GitHub** (patent priority guard, go/idf). `sil.py pr` will fail at the push step until Patent Counsel clearance; the human must then run the push with `ALLOW_PUBLIC_OSS_PUSH=1`. Never set that variable from the loop.
- `core/src/jmh/java` is compiled as a MAIN source root under `-Pjmh` → it sees only compile-scope deps (no `test-lib`, no `google-cloud-nio`). Hermetic helpers for benchmarks must be self-contained (see `InMemoryStorage` / `HermeticGcsFileSystem` in `core/src/jmh/.../client/`).
- Spotless does **not** cover `src/jmh/**`; format benchmark code by hand to Google style and have the critic check it.
- `GcsClientImpl` calls `createStorage()` from its constructor → subclasses must hand a fake `Storage` over via a static/ThreadLocal (pattern used by `FakeGcsClientImpl` and `HermeticGcsFileSystem`).
- HTTP read path touches only `Storage.reader(BlobId, BlobSourceOption...)` and `Storage.close()`; `GcsReadChannelMetadataExtractor` probes the SDK channel reflectively and falls back to `ItemInfoProvider` when absent.
- Default small-file footer prefetch window is 50 KB; a 64 KiB tail read bypasses `GcsFooterOptimizer` unless `analytics-core.small-file.footer.prefetch.size-bytes` is raised.
- `./mvnw -pl core test` runs only core's 165 tests (~15 s); the 1063 figure is the whole reactor. `-pl test-lib -am test` ≈ 75 s.
- **Line-budget estimation**: hygiene counts raw `git diff --numstat` (license header + package ≈ 24 lines per new Java file; google-java-format expands multi-arg calls with lambdas to ≥3–4 lines each). Budget ≥ 45 lines/file overhead; test-heavy PRs blow 400 lines fast → split test infra from tests up front.
- **`LocalStorageHelper` (google-cloud-nio `FakeStorageRpc`) zero-pads `ReadChannel` reads up to `limit()` when `limit > object size`** — real GCS does not. Don't use it as the oracle for limit-past-EOF; fine for the other `ReadChannel` contract cases.
- `GcsReadChannel` opens the SDK reader eagerly in its constructor (`SequentialReadStrategy`/`AdaptiveReadStrategy`), so `Storage.reader()` failures (e.g. 404) surface from `GcsFileSystem.open()`, not from `read()`; only read-time 404s become `FileNotFoundException`.
- `GcsClientImpl.getGcsItemInfo` **throws** `GcsExceptionUtil.createFileNotFoundException(itemId)` for a missing object; `GcsItemInfo.createNotFound` is only used for buckets. Fakes overriding `getGcsItemInfo` must throw, not return NotFound (critic caught this in PR A).
- `java.lang.reflect.Proxy` routes `equals/hashCode/toString` through the handler — a fail-loud handler must special-case `method.getDeclaringClass() == Object.class`.
- Any executor a fake hands to `GcsClientImpl`/`GcsFileSystemImpl` must use daemon threads, or a forgotten `close()` hangs test JVMs and JMH forks.
- Root `maven-compiler-plugin` config is in `<pluginManagement>` and inherited; a child module adding a processor must use `<annotationProcessorPaths combine.children="append">` or Error Prone silently disappears (verified via `[SelfAssignment]`). Configuring `<excludes>` on `maven-compiler-plugin` inside a profile (`-Pjmh` in `benchmarks/pom.xml`) merges element-by-element with the module-level `combine.children="append"` processors and parent Error Prone args without needing to duplicate them.
- Root `<dependencyManagement>` manages artifactId `core` (nonexistent), not `gcs-analytics-core` — declare the core dep with explicit `${project.version}`.
- `-pl <module>` without `-am` resolves sibling SNAPSHOTs from a stale `~/.m2` — always add `-am`.
- `GcsFooterOptimizer` only engages for object names ending in `.parquet`/`.orc`; hermetic footer benchmarks must keep the suffix. JMH `Blackhole` needs the magic password string when constructed outside the JMH runner (smoke tests).
- JMH class-level annotations (`@BenchmarkMode`, `@OutputTimeUnit`, `@Fork`, `@Warmup`, `@Measurement`, `@State`) are `@Inherited`, so a package-private `HermeticBenchmarkBase` in the same package cleanly shares setup/teardown and JMH config across benchmark classes while JMH's annotation processor generates `jmhType` subclasses for each concrete benchmark.
- `SmallObjectOptimizer` is only attached by `SmartReadChannel` when `GoogleCloudStorageInputStream` is opened with a known file size (`GcsFileInfo` or `URI`, not bare `GcsItemId`).
- Use `fileSystem.getCacheManager().invalidateSmallObject(itemId)` (or `invalidateFooter(itemId)` / `invalidateAll()`) to benchmark cold-cache reads against a trial-scoped `GcsFileSystem` without measuring `GcsFileSystemImpl` thread-pool creation/shutdown per invocation.
- `InMemoryStorage.ByteArrayReadChannel` opens streams lazily on `read(ByteBuffer)` (throwing 404 on `read` for missing objects, which `GcsReadChannel` translates to `FileNotFoundException`) and invalidates the active stream when `seek(long)` or `limit(long)` changes position/limit after a read, so `readerOpens()` counts actual media GET streams (warm `SmallObjectCache` hit = `0` opens; `readTailWithFooterPrefetch` = `1` open; `SequentialReadStrategy` with >128 KiB forward seek = `2` opens).
- `GcsReadChannelOpenBenchmark` showed `openAndReadOneByte_withItemId` was **3.3× slower** (`2.96 µs/op`, `9,432 B/op`) than `openAndReadOneByte_withFileInfo` (`1.18 µs/op`, `3,048 B/op`) because `GcsReadChannelMetadataExtractor` walked the class hierarchy and cloned `Method[]` per open; fixed in `20261027-095436-cache-metadata-extractor-reflection` (PR #421) via `ClassValue` caching (`0.89 µs/op`, `-70.1%` latency; `2,516 B/op`, `-73.3%` alloc).
- `AbstractReadStrategy.skipInPlace` previously allocated a `128 KiB` `skipBuffer` per strategy instance on forward seeks within `inplaceSeekLimit` (`140.5 KiB/op` in `ReadStrategyBenchmark.seekAndRead(forwardGapBytes=4096|65536)`); fixed in `20261027-140432-reuse-threadlocal-skip-buffer` (PR #422) via `ThreadLocal<SoftReference<ByteBuffer>>` (`9.4 KiB/op`, `-93.3%` alloc; `-63.2%` to `-73.3%` latency across all 6 forward-gap cases, and `-51.9%` alloc / `-36.3%` latency on `HermeticInputStreamBenchmark.positionedReads{objectSize=1048576}`).
- When caching reflective `Method`s via `Class.getMethods()`, wrap `method.setAccessible(true)` in `try ... catch (RuntimeException)` because JDK 9+ throws `InaccessibleObjectException` for methods on non-public classes in closed modules; `Files.readAttributes(FileSystems.getFileSystem(URI.create("jrt:/")).getPath("/"), BasicFileAttributes.class)` (`jdk.internal.jrtfs.JrtFileAttributes.size()`) deterministically exercises this in unit tests across all OSes.
- In JMH benchmarks of callback APIs (`OperationListener`), empty callback bodies allow C2 to inline and scalar-replace the argument objects (`MetricKey`, `Collections.singletonMap`); consuming `operation.getName().hashCode() ^ metrics.size()` into a `volatile long` sink increased `recordMetric(listenerCount=1)` from `3.0 ns/op` to `11.7 ns/op` (and `listenerCount=8` from `7.6 ns/op` to `41.4 ns/op`). `Telemetry.measure` costs ~1.3 ns/op with 0 listeners vs ~165 ns/op with 1 listener (`Operation.newOperationId` UUID formatting + `ConcurrentHashMap` + `MetricKey` allocation).

## Benchmarks
- **Hermetic benchmarks are merged on `main` (`#407`–`#412`)** under `benchmarks/src/main/java/com/google/cloud/gcs/analyticscore/benchmarks/` (7 suites / 45 cases). `gates.perf` in `.sil/loop.yaml` runs all 45 cases directly from `benchmarks/target/classes` with `-prof gc` and no `SIL_GCS_TEST_BUCKET` requirement, evaluating Class D (`readerOpens/op`, `bytesServed/op`), Class S (`gc.alloc.rate.norm` in `B/op`), and Class P (`primaryMetric` latency).
- **`IoCounters` (`@AuxCounters(Type.EVENTS)`)**: `IoCounters.record(storage)` accumulates (`+=`) per-invocation deltas within each measurement iteration; both `sillib/jmh.py` (`_normalize_io_samples`) and Kokoro's `compare_benchmark` (`extract_io_counters`) normalize `readerOpens` and `bytesServed` per operation using `est_ops = meas_time_s / (lat * unit_sec)` and `(b_raw / o_raw) * o_per_op` (`sd = 0`). PR `#414` wired `IoCounters` into the remaining `HermeticInputStreamBenchmark` methods (`sequentialRead`, `readTailWithFooterPrefetch`).
- First smoke numbers (1 MiB, JDK 17, noisy box): sequentialRead ≈ 260 µs, readVectored ≈ 345 µs, readTail ≈ 63 µs, positionedReads ≈ 3.8–10 ms (64 opens; ~275 KB allocated per open → **perf lead: per-open allocation in the channel/strategy stack**). positionedReads varied 2.7× between short runs — needs the full `-f 2 -wi 3 -i 5` and a measured CV% before use as a gate target.
- Every class in the original `core/src/jmh` (TelemetryBenchmark, SmallObjectCachingBenchmark, ParquetFooterParsingBenchmark, ParquetRecordReadBenchmark, GcsReadChannelBenchmark) calls `IntegrationTestHelper.uploadSampleParquetFilesIfNotExists()` and needs `-Dgcs.integration.test.bucket`; they are Tier-2 (real GCS) benchmarks and should never gate small deltas.
- Benchmarks considered trustworthy (low CV%): _fill after first JMH baseline_.
- Minimum JMH settings for a believable verdict: `-f 2 -wi 3 -i 5` (raise forks for noisy ones).

## Where the opportunities usually are
- **Measured I/O shape over the in-memory fake (1 MiB object, default options, 128 KiB footer prefetch) — concrete perf leads:**
  - 64 × 4 KiB positioned reads (`readFully`) → **109 SDK reader opens and ~17.5 MB served** to deliver 256 KiB (adaptive/sequential strategy skip-in-place re-reads); ~275 KB allocated per open.
  - `sequentialRead` of 1 MiB with 64 KiB buffers → **9 reader opens**, 1.19 MiB served.
  - `readTail` with footer prefetch → 3 opens, of which **2 are eager opens that serve 0 bytes** (`GcsReadChannel` ctor opens a sequential SDK reader for the stream and again for `readTail()`'s temporary channel); the optimizer then issues exactly one bounded 128 KiB read.
  Each is a self-contained `perf(client|core)` candidate with a zero-noise counter metric (opens/op, bytes/op) plus B/op.
- Coverage is already high: line 84.41% / branch 66.07% at baseline `a890372628`; the lowest-covered real classes are `OpenTelemetryReporter` (88%), `CloudMonitoringOpenTelemetryProvider` (90%), `GcsTransportOptionsFactory`, `GcsFileSystemOptions`. The rest of the gap is `AutoValue_*` generated code (excluded from scout). Branch coverage (66%) is the better test target.
- Highest churn (90d): `client/.../GcsClientImpl.java`, `GcsFileSystemImpl.java`, `auth/GcsAuthOptions.java` — candidates for refactor/fix work and where regressions are most likely.
- Open upstream issues worth a look: #174 (vectored read API improvements).
- Landed as draft PRs 2026-10-19 (do not re-scout): #404 bidi vectored coalescing, #405 footer-cache vectored tail ranges, #406 zero-length/negative vectored range validation. ## Change-type recipes
- **perf**: profile first (async-profiler at `/home/ajayky_google_com/async-profiler-2.9-linux-x64/build/libasyncProfiler.so`), make one change, prove it with the JMH verdict table.
- **test**: target a class from the lowest-coverage list; use fakes from `test-lib` over mocks; AAA structure; Truth assertions.
- **fix**: reproduce with a failing unit test first; keep the fix minimal.
- **refactor**: behaviour-preserving; coverage must not drop; perf must show NO_CHANGE or better.

## Do-not-repeat list
- **Do not share `GcsFooterOptimizer` / `SmallObjectOptimizer` instances across concurrent `GoogleCloudStorageInputStream.readFully` calls**: `GcsFooterOptimizer` has 9 non-volatile, unsynchronized mutable fields (`localFooterBuffer`, `localBufferStartPosition`, `fileSize`, `pendingSpeculativeBuffer`, etc.); `adoptFooterBuffer` writes `localFooterBuffer` before `localBufferStartPosition`, creating a publication race where concurrent threads can read corrupted bytes from offset `position + 1`.
- **Do not replace `ByteBuffer.allocate(prefetchSize)` with `footerView.slice()` in `GcsFooterOptimizer.toCanonicalFooter`**: `footerView.slice()` retains a strong reference (`HeapByteBuffer.hb`) to the `2 * estimatedPrefetchSize` (`256 KiB`) speculative backing array inside the global Caffeine `footerCache` while `AnalyticsCacheManager` weighs entries by `value.remaining()` (`128 KiB`), silently doubling retained old-gen heap memory.
